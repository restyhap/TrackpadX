# 01 - 需求分析：自定义触控板手势

> 状态：v2（三项决策已确认，待办见第 7 节）
> 目标平台：macOS 27（Golden Gate）

---

## 1. 背景与问题

- macOS 系统设置 > 触控板中的手势为系统内置固定集合（如三指上滑调度中心、四指捏合启动台等），用户只能开关或在有限选项间切换，无法自定义手势与动作。
- 用户希望支持自定义手势，第一步先实现：**三指下滑 -> 对当前聚焦（前台）应用执行某个动作**。

## 2. 目标

- G1：识别用户自定义的触控板手势（第一期：三指下滑）。
- G2：手势触发后对当前前台应用执行指定动作（动作类型待定，见第 7 节）。
- G3：手势与动作的映射可配置（第一期可硬编码，后续可扩展）。

## 3. 范围

### 3.1 第一期（本期）范围
- 仅支持三指下滑单一手势的识别。
- 仅作用于当前前台应用。
- 运行于 macOS 27，后台常驻运行。

### 3.2 非目标（本期不做）
- 不做手势录制/编辑界面。
- 不做多手势组合、四指及以上手势、点按类手势。
- 不做按应用区分的手势覆盖规则。
- 不接入 Magic Mouse 手势。

## 4. 功能需求

| 编号 | 需求 | 验收标准（草案） |
|---|---|---|
| FR-1 | 在触控板上识别三指下滑 | 三指同时按下并向下位移超过阈值时触发一次；上滑、横滑、两指、四指不触发 |
| FR-2 | 手势触发后对前台应用执行动作 | 动作仅作用于触发时的前台应用，前台应用切换后目标随之变化 |
| FR-3 | 防误触 | 手指数量变化、位移不足、速度异常时不触发；同一次手势只触发一次 |
| FR-4 | 与系统手势共存 | 手势冲突时需明确告知用户，不得静默失效或与系统动作同时触发而无提示 |
| FR-5 | 权限引导 | 缺少辅助功能/输入监控权限时，应用给出明确提示并引导授权 |
| FR-6 | 稳定性 | 事件 tap 被系统禁用后自动重新启用；异常时功能降级而非导致系统手势失效 |

## 5. 非功能需求

- NFR-1 延迟：从手势结束到动作执行的感知延迟应可接受（目标 < 200 ms，待实测确定）。
- NFR-2 资源：后台常驻时 CPU 占用应接近空闲水平。
- NFR-3 安全合规：依赖私有框架的部分不能上架 Mac App Store，需在分发方式上提前决策。
- NFR-4 可维护性：手势识别层与动作执行层解耦，便于后续扩展手势与动作。

## 6. 技术调研结论

### 6.1 Golden Gate（macOS 27）相关背景

- "Golden Gate" 即 macOS 27 的版本代号，Apple 官方发布说明页面为 `developer.apple.com/documentation/macos-release-notes/macos-27-release-notes`。
- macOS 27 的 AppKit 变化集中在 **NSGestureRecognizer**（应用内视图手势）：新增 `exclusiveGestureBehavior`、`cancellableByScrollGesture`、`NSGestureRecognizerSuppressesMainMenuActions` 等。这些 API 只作用于**本应用视图内**，**无法**捕获系统级、全局的触控板手势，因此不能直接用于本需求。
- 已知问题（来源：Mac Mouse Fix issue #1873、MacIgniter、macworld.info 兼容性追踪）：macOS 27 不再读取第三方工具通过写入未公开字段模拟的触控板手势，导致依赖此方式的工具（如 Mac Mouse Fix）调度中心、切换桌面等动作失效。**这意味着不能依赖"模拟/伪造手势事件"的方案在 macOS 27 上工作，应以"读取真实触控数据"为主。**

### 6.2 技术路线对比

| 路线 | 原理 | 主要 API | 优点 | 缺点 / 风险 |
|---|---|---|---|---|
| A. 公开 API：手势事件 tap（推荐首选） | 用 `CGEvent.tapCreate` 监听 `NSEvent.EventTypeMask.gesture`，通过 `NSEvent(cgEvent:)` 的 `allTouches()` 取得每根手指的 `NSTouch`（含 `phase`、`identity`、`normalizedPosition`） | `CGEvent.tapCreate`、`NSEvent(cgEvent:)`、`NSTouch` | 公开 API 为主，相对稳定；手势事件在手指按于触控板期间持续派发，不依赖系统是否识别出手势 | 文档对触控事件类型描述有限（需参考实现）；`NSTouch` 无接触面积，无法做palm rejection；系统手势可能仍会触发；需辅助功能/输入监控权限 |
| B. 私有框架 MultitouchSupport | `dlopen` 加载 `MultitouchSupport.framework`，`MTDeviceCreateList` + `MTRegisterContactFrameCallback` 获取原始接触帧（位置、接触面积、压力、角度） | `MTDeviceCreateList`、`MTRegisterContactFrameCallback`、`MTDeviceStart` | 数据最完整，可区分设备（触控板/Magic Mouse），可做 palm rejection | 私有 API，结构体布局无官方保证，macOS 升级可能失效；不能上架 App Store |
| C. 模拟手势（Dock Swipe 事件） | 构造私有字段的 `CGEvent` 模拟三/四指滑动 | 私有字段（dockswipe / Mac Mouse Fix 方案） | 可用于自动化测试 | **macOS 27 上字段方式已失效**，需改用 `IOHIDEvent` + `CGEventSetHIDEvent`，且该路径未经充分验证；不适合作为识别方案 |
| D. 应用内 NSGestureRecognizer / NSResponder 手势 | 在视图中实现 `swipeWithEvent:` 等 | AppKit | 公开、简单 | 仅限本应用窗口内，无法全局识别，**不满足需求** |

**初步结论**：
- 识别层首选 **路线 A**（公开 `CGEvent` 手势 tap + `NSTouch`），参考 AltTab 的实现经验（`src/events/TrackpadEvents.swift`，见下方“实现经验”）。
- 若路线 A 在 macOS 27 上数据不足（如需要更精确的位置或单指/Magic Mouse 数据），再评估 **路线 B** 作为备选，但需接受私有 API 风险。
- 动作层使用公开 API：`NSWorkspace.shared.frontmostApplication` 获取前台应用，`NSRunningApplication.hide()` / `terminate()` 等执行动作。
- 路线 C、D 不作为本需求的识别方案。

### 6.3 实现经验（来自 AltTab 与社区实践，需在 macOS 27 实机验证）

1. **tap 类型**：主动式 tap（`cghidEventTap` + 可拦截）会让 WindowServer 等待本进程处理每个手势事件，手指按住期间会影响光标移动。建议拆分为：
   - 监听型（listen-only）tap：仅做识别；
   - 仅在可能触发手势时才启用的主动 tap：用于吞掉事件（如需要）。
2. **线程**：`NSEvent(cgEvent:)` 必须在主线程调用，否则 AppKit 崩溃。
3. **异常**：`NSTouch.normalizedPosition` 对部分间接触控（如 Universal Control 转发）会抛 `NSInternalInconsistencyException`，Swift 无法直接捕获，可能需要 Objective-C 垫片。
4. **系统手势无法被"吞掉"**：从 tap 返回 `nil` 只能阻止前台应用看到手势，不能阻止 WindowServer 处理四指捏合等系统手势。三指下滑是否与系统 App Exposé 等动作冲突，需在 macOS 27 上实测确认（见第 7 节）。
5. **TCC 权限**：需要辅助功能（Accessibility）权限；输入监控（Input Monitoring）权限是否需要，需实测确认。

### 6.4 三指下滑识别算法（初版设想）

1. 监听手势 tap，按事件统计当前接触的手指数（`allTouches()` 中 `phase` 为 began/moved 的数量）。
2. 当接触手指数恰好为 3 时，记录起始质心（各手指 `normalizedPosition` 的均值）。
3. 质心沿 y 轴向下位移超过阈值（如 0.15 归一化单位，待调参），且水平位移占比较小，判定为"三指下滑"。
4. 手指数变化或超时则取消识别；成功触发后设置冷却时间，避免一次手势重复触发。

## 7. 用户已确认的决策（2026-10-09）

1. **分发方式**：必须能上架 Mac App Store → 全程公开/沙盒允许的 API，沙盒开启。
2. **动作定义**：三指下滑 → **最小化当前前台应用的聚焦窗口**。实现方式与系统现有手势监控机制一致（listen-only 监听，不拦截/不合成事件，纯"补强"，避免冲突）。
3. **运行形态**：**不做状态栏图标**。设置入口集成到系统设置中；点击设置项可进行开启/关闭、开机自启（Login Item）等配置。
4. **多项目形态**：用户已有一个触控板防误触项目，计划将其与本功能合并为一个多功能的"触控板工具"应用，设置项以**可扩展列表**呈现（每个小功能一项，可同时设置多个）。

### 7.1 决策引发的技术验证结论

| # | 问题 | 结论 | 依据 |
|---|---|---|---|
| 1 | 沙盒 App 能否全局监听手势事件？ | **可以**。用 `CGEvent.tapCreate`（listen-only）+ **输入监控（Input Monitoring）权限**。这是公开、沙盒允许的路径；不使用 `NSEvent.addGlobalMonitor`（需辅助功能权限、沙盒语义不清，且审核风险高） | Apple 开发者论坛（eskimo/Quinn 官方回复）：`CGPreflightListenEventAccess` / `CGRequestListenEventAccess` 配套 `CGEventTap`，macOS 10.15 起与沙盒兼容 |
| 2 | 沙盒内能否注入事件？ | **不能**，`CGEvent.post` 完全被沙盒封死，无 entitlement 可开。但本需求只需监听 + 最小化窗口，不需要注入 | quicopy.com App Store 上架实测记录 |
| 3 | 最小化窗口怎么实现？ | 公开 API：`NSWorkspace.shared.frontmostApplication` 取前台应用 → 通过 AXUIElement（辅助功能权限）或该 App 的 `NSRunningApplication`/AppleScript 执行 minimize。仅当合成键盘事件不可行时才走 AX 路径；优先尝试无损方案（见 8.x 待验证） | — |
| 4 | 能否把设置面板放进系统设置侧边栏？ | **不能（App Store 途径）**。现代系统设置面板用**未公开**扩展点 `com.apple.Settings.extension.ui`（`.appex`），仅 Apple 签名可用；旧 `.prefPane` 是 System Preferences 时代的遗留机制，在 macOS 27 已边缘化、且与沙盒/App Store 冲突。第三方能出现在系统设置里的只有：登录项、Finder/Share 等**已定义**扩展点，没有"自定义设置面板"扩展点 | Paradise Facade 博客（FruitMenu Redux 调研）、`/System/Library/ExtensionKit/Extensions` 逆向记录：该扩展点未公开给第三方，无 restricted entitlements 无法注册 |
| 5 | 替代设置入口？ | ① 应用内设置窗口（SwiftUI，符合系统设置风格）；② 系统设置 > 登录项与扩展中会出现该 App 的登录项开关（系统自带）；③ 可用 `x-apple.systempreferences:` URL 深链直接跳到权限/登录项面板，减少用户操作 | Apple 支持文档、开发者论坛 |

> ⚠️ 用户预期"设置项出现在系统设置侧边栏"目前**无法通过 App Store 合规途径实现**。已在第 5 点给出替代方案。
